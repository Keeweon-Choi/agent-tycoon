# Agent status tracking and context usage

> Read before touching transcript parsing, file watching, hook-vs-heuristic detection, permission or idle timers, or the context gauge.

## Agent Status Tracking

JSONL transcripts at `~/.claude/projects/<project-hash>/<session-id>.jsonl`. Project hash = workspace path with `:`/`\`/`/` → `-`.

**JSONL record types**: `assistant` (tool_use or thinking), `user` (tool_result or text prompt), `system` with `subtype: "turn_duration"` (reliable turn-end signal), `progress` with `data.type`: `agent_progress` (sub-agent tool_use/tool_result, non-exempt tools trigger permission timers), `bash_progress` (Bash output — restarts permission timer), `mcp_progress` (MCP tool — same timer restart). Also observed but not tracked: `file-history-snapshot`, `queue-operation`.

**File watching**: 500 ms polling with partial-line buffering for mid-write reads. Tool-done messages delayed 300 ms to prevent React batching from hiding brief active states.

## Dual-mode detection

| Mode                     | Source                                                 | Detection                                                                                                                                                                                                                                                                         |
| ------------------------ | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Hooks** (preferred)    | Claude Code Hooks API → HTTP POST → `HookEventHandler` | Instant, reliable. Installed events are `CLAUDE_HOOK_EVENTS`. `UserPromptSubmit`/`TaskCreated` are deliberately NOT installed — they normalize to null, so installing them only forwarded prompt text to be dropped; `normalizeHookEvent` still tolerates them for stale installs |
| **Heuristic** (fallback) | Polling JSONL files                                    | Per-agent 500 ms JSONL polling; 3 s external scanner; 30 s stale check (the terminal-focus /clear heuristic and terminal adoption were deleted with the VS Code extension; hooks handle /clear)                                                                       |

The `hookDelivered` flag (per agent) and `hooksEnabled` (global) gate timer logic. JSONL polling always runs in both modes for tool content (status text, animations); only permission (7 s) and text-idle (5 s) timers are suppressed by `hookDelivered`.

## Sub-agent permission detection (heuristic)

When a sub-agent runs a non-exempt tool, `startPermissionTimer` fires on the parent agent. If `PERMISSION_TIMER_DELAY_MS` (7 s) elapses with no data, permission bubbles appear on both parent and sub-agent characters via `agentToolPermission` + `subagentToolPermission` broadcasts.

`activeSubagentToolNames: Map<parentToolId, Map<subToolId, toolName>>` tracks which sub-tools are active for the exempt check. Cleared when data resumes, Task completes, or `turn_duration` arrives.

**Timing budget for tests**: the test waits for the bubble AFTER waiting for the "Subtask:" overlay. But the Subtask overlay appears when the parent's **Task tool_use** is parsed (scenario time T), while the timer only starts when the **sub-tool tool_use** in the progress record is parsed (~1 s later). Plus 7 s timer + 300 ms IPC/render slop = a wait timeout less than ~10 s is unsafe.

## Permission waits of engine sessions (PERM-PROMPT)

Claude Code asks some permissions even in bypass mode (a background sub-agent's "Dangerous rm ..." check), and a bypass session gets no heuristic permission timer. For engine-run background sessions the precise signal is `claude agents --json`: the row says `waitingFor: "permission prompt"` (`state: blocked`). `server/src/cld/permissionWait.ts` runs that check only on a cheap trigger: a heuristic `agentToolPermission` / `subagentToolPermission`, an engine lead's (or its sub-agent's) tool call open `PERMISSION_WAIT_SUSPECT_MS` (hooks mode too), or a message the messenger holds for it; at most one run per `PERMISSION_WAIT_CHECK_MS`, re-checked at that pace only while a wait is confirmed. Nothing waiting and nothing suspected: no timer but the per-open-call ones, no spawn. A confirmed wait is one episode: the office broadcasts the lead's `agentToolPermission` (with `asker`, the sub-agent's staff name id, when one asks, plus its `subagentToolPermission`), which carries the bubble, the 🔐 notice and Web Push; the messenger contact gets `permission`: while someone views that conversation, the dialog itself, read off the session's screen once per wait (one attach, read, detach; a whole dialog only, its rule visible), else the asker's newest open call from the lead's or sub-agent's transcript (an older open call may be done with its result unread); it ends with `agentToolPermissionClear` when the row no longer says permission. 허용/거부 on the card (`permissionAnswer`, privileged) go through `ChatManager.answerPermission`: on the attach's screen it presses `1` (allow, never a "don't ask again" option) or Esc only when a permission dialog is up right now and is exactly the screen card's dialog (or, for a transcript card, shows its description and command), then waits for it to go; anything else sends nothing and says so. `held()` also holds a session whose row waits for a permission prompt, so queued messages wait (and say why) until the dialog is answered.

A PTY agent (TERM-P3) asks through its PermissionRequest hook (`agty permission-hook` -> control `permission-hook` -> `OfficePermissions.ask`): the card is the hook's, 허용/거부 its decision, no answer in `PTY_PERMISSION_WAIT_MS` none (Claude shows its own dialog). A daemon that goes while the hook waits (a deploy restart) is asked again by the hook, the same call with the rest of its time (`waitMs`, up to 60 s away), and the new daemon waits up to `PTY_PERMISSION_READY_MS` for the engine to find the agent, counted inside the hook's own time (never on Windows: the pipe name is machine-wide). A hook card's id names the daemon's start (`hook:<boot>:<n>`), so an answer to an earlier daemon's card is `gone`; the webview never queues a `permissionAnswer` across a disconnect (the card's buttons are off while disconnected); a hook that hangs up takes its card with it. A permission dialog the terminal holds with no hook behind it (OSC 7501 `blocked:kind=permission` from the PTY host: the hook gave up, or before it asks again) is a card too, `toolId: ''`, no 허용/거부, 터미널에서 보기, with the bubble and the notice (`OfficePermissions.syncPty`), gone when the terminal's dialog is. In the bell, a 허락을 기다려요 of an engine lead whose contact carries no card says 더 기다리지 않아요 and opens the terminal (`permissionOver`).

## Context usage (server/src/contextUsage.ts)

Every agent's context gauge. Fed from `message.usage` on assistant records by `processTranscriptLine`, broadcast as `agentContextUsage` and rendered by `ToolOverlay`.

- **Snapshot, not a total.** Context = the newest turn's `input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens`. Summing turns measures spend, not occupancy, and misses the cached tokens that ARE the context (`input_tokens` is single digits once caching kicks in). Falls on compaction and `/clear` for free.
- **All-zero usage means "no news"** — synthetic records (API errors, interrupts) report zeros and must not blank the gauge.
- **Sidechain rule**: a lead's sidechain records are its sub-agents' turns and must not move its gauge; a teammate's own transcript is sidechain top to bottom and would otherwise never report. Positional latch (`sawMainChainUsage`): once a file produces a main-chain turn, later sidechain records belong to someone else.
- **The window comes from the provider**, not from the runtime: `HookProvider.contextWindowForModel(model)` (Claude: 1M for the current Opus/Sonnet/Fable line or a model id ending `[1m]`, 200k for Haiku and the older models, `undefined` for any id outside the table: another vendor behind a proxy, a family name we never listed). Transcripts state usage but never the limit, and guessing 200k for a 1M model reads five times too full. `widenContextWindow` only ever widens a table window, since a context that doesn't fit disproves the assumption while a shrinking one proves nothing.
- **Where the limit comes from (`limitBasis`, FR-STA-005).** `agentContextUsage.limitBasis` is `reported` (the id carries `[1m]`: the CLI stated the window), `estimated` (a table name; also a window widened because the context outgrew it) or `unknown` (no model seen yet, or a model the table does not know). `HookProvider.contextWindowBasis(model)` says which; a record that names no model (a compaction boundary) leaves the last word standing. The screens read it: `estimated` shows `≈` and the hover "Estimated: the limit was picked from the model name" on the office gauge, the nameplate and stat card, the party card, the board; `unknown` shows the token count only (no bar, no percent, no fatigue behaviours: `fatigueFor` is null) and says why on hover. A server that sends no basis is read as an estimate. The engine's renew judgement (85% fill) already treated an unknown model as "not full" and still does.
- **Compactions are counted by the daemon, not guessed from the gauge.** Every Claude agent's `compact_boundary` record goes through `updateContextUsage`, which counts it (`AgentState.compactions`) and keeps the newest `COMPACTION_LOG_KEPT` (5) as `{at, trigger?, preTokens?, postTokens?}`: `at` is the record's own `timestamp` (the daemon's clock when it has none), `trigger` is `auto`/`manual` and the token counts are there only when the record carried them (a missing field is missing, never invented). It follows the same sidechain rule as the gauge (a lead does not count its sub-agents' boundaries). The count goes out as `agentCompactions {id, count, partial?, recent}` when one happens, in `resendAgentActivity` to a client that connects later, and for a watched sub-agent through `SubagentWatch.onCompactions` into its employee's `TempEmployee.compactions`. A new transcript (`/clear` swap, a teammate's next file) starts the count over (`resetCompactions`). The webview shows `max(engine row's count, the daemon's)` as the "휴식 N"; the old guess (a gauge falling more than `compactionDrop` points) and that ez-rules number are gone. Engine projects keep their own `CompactionWatch` count and `compacted` events; the two agree on a conversation read from the start.
- **Mid-session agents count a floor.** An agent adopted or restored at end-of-file would never replay its earlier boundaries, so `seedCompactions` (in `startFileWatching`, next to `seedContextUsage`) counts the boundaries in the `CONTEXT_SEED_TAIL_BYTES` before `fileOffset` and nothing after it (that is the stream's). When the transcript is longer than the tail, `partial: true` and the screens write `≥N`. Not persisted: a restart counts again from the tail.
- **`seedContextUsage` runs once per agent in `startFileWatching`** — the single seam every watched agent passes through. Agents adopted or restored mid-session start at end-of-file, so without a tail read they'd have no gauge until their next turn.
- Sub-agents get no `agentContextUsage` of their own (no session of their own); the shadow store hands a watched sub-agent's context to `SubagentWatch.onContext` only, which cld-gui's staff roster (`server/src/cld/tempStaff.ts`) shows as the employee's fatigue.

## Questions that survive a restart (WAITING-PERSIST)

A question is a main turn that ended asking: its last main-chain assistant text (`AgentState.lastAssistantText`, kept by `processTranscriptLine`, reset by a user prompt) ends with `?` or `？` once trailing whitespace, markdown emphasis, closing quotes and brackets are stripped (`endsWithQuestion`); a text that ends with code (inline code, a closing fence) or inside an open fence is no question, and only the person's own agents ask (not a teammate or sub-agent). `settleQuestion` (`server/src/question.ts`) decides it at every turn end the server already sees: the `turn_duration` record, the text-idle timer (a text-only turn has no `turn_duration`; this is how an agent without hooks, such as our PTY engine Leads, ends a question turn), and the Stop hook. With hooks the text-idle timer is off and a text-only turn has no `turn_duration`, so the Stop hook is the only turn end: it first reads the transcript's new lines with the poll's reader (`readNewLines`), since the Stop can arrive before the 500 ms poll has read the turn's last text. Claude's `Notification` `idle_prompt` (60 s without input after ANY turn) is no question: it keeps its `awaitingInput` "Waiting for input" label and notice, and leaves the question as it is. The question is `questionOffset` on the agent (the transcript's size then), saved in its own office file `questions.json` (keyed by transcript, at most `QUESTIONS_MAX`, 0600, tmp+rename; in memory only until `cli.ts` calls `useQuestionStore()`, so tests never reach a real home). The next tool call or user prompt ends it. `agentStatus` carries `question: true` while it stands, and `resendAgentActivity` sends it to a browser that connects later. Web Push sends a question turn once (`PushService.turnPushed`), with the turn end's text preview and room routing, as a question; `idle_prompt` keeps its own generic push. On start `restoreQuestion` gives it back when the transcript is bound again (`CharacterBinder.bind` for the office's characters, `restoreExternalAgents` for external ones) only when the transcript has no `user`/`assistant` record past `questionOffset` (`answeredSince`); otherwise the entry is dropped. A question given back at bind is broadcast with `restored: true` to the browsers already connected: shown, with no notice, sound or push. Entries whose transcript is gone are dropped on load. Nothing here sends anything to an agent. An open `AskUserQuestion` counts as a question in the webview but is not restored after a restart. In the webview `waitReasons` (`webview-ui/src/cld/waiting.ts`) is the one rule for "waiting for the person" (permission or question) every surface reads.

## One state for an engine session (STATE-SYNC)

For a session the engine runs, the engine's word is the state on every screen (character and card, party, messenger, dev room board, workbench, status panels): `webview-ui/src/cld/turnState.ts` (`engineTurn`, `sharedActivity`, `rowBusy`). At work while the row says `busy`, `renewing` or `shellWait` (Claude Code's session status `shell`: the turn is over but a background shell it started, a job or a Monitor, still runs; Claude Code itself calls that Working; `busy` stays false so messages go in); resting when the row says not busy, and off when it is off. Waiting on the person still comes first, and an open tool row is work even before the next snapshot. A job wait shows as ⏳ 잡 기다리는 중 and keeps the character at its desk, so the 30-minute rules (the board's 끝남/쉬는 중, the 야근 grace) never fire during it. Sessions the engine does not run keep the tool-row rule. `cld/test/run-state-sync.ts` reads every surface in a long call and a job wait.
